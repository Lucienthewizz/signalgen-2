## Ringkasan yang bisa disampaikan

“SignalGen sekarang difokuskan sebagai web multi-user. Pada Model A, indikator
dihitung di browser melalui Go/WASM, sedangkan rule/keputusan privat tetap di
server Go melalui WebSocket. Supabase menangani identity dan penyimpanan Postgres.
Backend memeriksa sesi, kepemilikan data dan hak fitur. Integrasi, tes keamanan
utama dan demo screening tiga saham dengan akun nyata sudah berjalan;
evaluasi efisiensi lengkap masih perlu dituntaskan.”

Sebut hasilnya **screening historis berbasis rule**, bukan prediksi harga berbasis
ML, feed resmi IDX realtime, atau rekomendasi keuntungan. Login bukan bukti bahwa
akun otomatis berhak memakai seluruh fitur.

## Hubungan komponen

```text
Login Supabase → bearer identity → app-session + entitlement server
  → rule yang diizinkan + universe milik user → snapshot historis privat
  → browser worker Go/WASM menghitung indikator setiap series
  → gabungkan kandidat → satu compute grant + one-use ticket
  → satu WebSocket → Go menilai rule privat → hasil per simbol + bukti indikator
```

Auth menjawab “siapa user ini?”. Authorization menjawab “fitur dan data apa yang
boleh digunakan?”. WebSocket adalah jalur pesan, bukan database. pgx menyimpan
data ke Postgres dengan owner filter. WASM bukan DRM; indikator yang dikirim ke
client tetap dapat dianalisis, sehingga rule system privat tidak ikut dikirim.

## Pengukuran, beserta batasnya

Microbenchmark kernel di Apple M5, Go 1.27.1, fixture 40 candle/21 kandidat,
tiga pengulangan pada 6 Oktober:

| Model | Waktu kernel per operasi | Alokasi per operasi |
| --- | --- | --- |
| A: private decision | 2.611–2.795 ns/op | 1.392 B/op, 4 allocs/op |
| B: private critical indicator | 2.918–2.935 ns/op | 3.120 B/op, 6 allocs/op |

Titik pada tabel adalah pemisah ribuan. Angka ini hanya pekerjaan kernel yang
dibandingkan, tidak memasukkan browser/Auth/database/network/TLS. B/op adalah
alokasi, **bukan peak RAM**. Fixture payload pembanding terdahulu: A 3.334 byte,
B 2.994 byte; jangan mengatakan Model A selalu lebih kecil di jaringan.

Tes transport Model A memakai 250 kandidat/batch dan identitas simulasi berbeda:

| Concurrent user | Warm batch selesai | Gagal | Warm p95 |
| --- | --- | --- | --- |
| 1 | 8 | 0 | 0,982 ms |
| 10 | 80 | 0 | 3,282 ms |
| 30 | 240 | 0 | 8,030 ms |

Client/server harness berada di proses uji yang sama; identity, session,
entitlement, grant dan market data adalah adapter deterministik. Ini tes
transport/protokol lokal, bukan kapasitas production atau uji provider cloud.
CPU/RAM kedua sisi belum diukur terpisah, dan Model B belum menjalani transport
setara. Model A dipilih pengguna untuk implementasi; minta pembimbing menyetujui
metode evaluasinya, bukan menganggap microbenchmark sebagai keputusan final.

## Urutan demo 5–10 menit

1. Jalankan preflight di bawah sebelum pertemuan. Buka
   `http://127.0.0.1:5175/#login`, lalu login sendiri tanpa menampilkan password/token.
2. Tunjukkan profile, role/akses serta sesi perangkat. Jelaskan rule/universe
   milik user tidak dapat diakses akun lain.
3. Gunakan akun demo berizin yang dipilih pengguna; akses `screener` sudah ada
   sebelum pengujian dan tidak ditambahkan oleh agent. Akun sebelumnya tanpa
   akses tetap ditolak. Akun lain yang memerlukan grant harus melalui operator
   dengan expiry/audit reason, bukan perubahan metadata atau bypass guard.
4. Setelah diizinkan: pilih rule yang diperbolehkan dan universe pribadi berisi
   satu sampai tiga simbol katalog. Jalankan screening.
5. Jelaskan sumber historis, indikator di worker, satu batch/socket, lalu hasil
   per simbol beserta alasan dan timestamp. Jumlah sinyal tergantung dataset/rule;
   jangan memaksakan angka fixture sebagai hasil provider terbaru.
6. Akhiri dengan batas hasil dan rencana evaluasi berikutnya. Jangan mendemokan
   payment sukses, transaksi broker, atau P&L seolah sudah authoritative.

Uji browser nyata 6 Oktober berhasil: login → app-session → universe pribadi
`Demo asis 7 Oktober 2026` berisi BBCA/BBRI/TLKM → rule system Default Scalping
→ dataset historis Yahoo → worker WASM → grant/ticket → WebSocket → tiga baris
hasil. Ketiga hasil terbaru adalah `No match`, data quality `complete`, range
14 Mei–6 Oktober 2026. No match berarti kondisi rule tidak terpenuhi, bukan error.
Log aman mengonfirmasi satu prepare, satu grant, satu ticket dan satu upgrade
WebSocket; hasil terlihat di UI, bukan hanya status HTTP 101.

Agent membuat satu universe khusus demo pada akun tersebut; tidak mengubah
password, role, entitlement atau subscription. Dataset/grant/ticket adalah state
eksekusi, bukan ledger transaksi. Jangan menyimpan credentials demo di laporan
atau repository. Signup/recovery email belum diverifikasi oleh tes ini.

Uji tambahan: profile berhasil PATCH 200 dan dibaca kembali GET 200 setelah
reload; pengujian memakai nama yang sama sehingga tidak mengubah identitas
tampilan akun. UI sekarang menyimpan nama melalui backend dengan optimistic
version, sedangkan avatar tetap lokal. Conflict tidak ditimpa otomatis.

Rule pribadi `Rule demo asis — RSI 14 < 30` dibuat sebagai contoh yang dapat
diperlihatkan, tanpa mengubah rule sebelumnya. Pada dataset historis tersebut,
TLKM menghasilkan `Match` dengan RSI 27,28; BBCA/BBRI menghasilkan `No match`
dengan RSI 41,17/41,21. Ketiga series dievaluasi dan quality `complete`. Rule dan
universe demo dipertahankan pada akun untuk pertemuan. Ini bukti alur create
rule → rule tersimpan → screening, bukan bukti profit atau prediksi harga.

Connector juga diperbaiki: bootstrap sesi bersamaan tidak lagi saling
menggantikan, respons lama tidak merusak login baru, revoke meminta login ulang,
dan write yang expired tidak diputar ulang diam-diam. Otomatisasi refresh
identity/rotation tetap merupakan pekerjaan terpisah.

## Pemeriksaan sebelum demo

Dari root repository:

```sh
node backend/scripts/demo_preflight.mjs http://127.0.0.1:18090 http://127.0.0.1:5175
```

Harus delapan `PASS` dan exit 0. Checker hanya GET ke loopback, tidak membaca
`.env`, tidak memasukkan token dan tidak menampilkan body privat. Ia memeriksa
readiness, kesamaan kontrak API/proxy dan artifact WASM, bukan izin akun nyata.

Pada laptop ini API aktif adalah container `signalgen-web-integration-api`
di port 18090, terpisah dari container lama di 8080. Frontend aktif sudah memakai
proxy tersebut. Jika perlu menyalakan kembali frontend, dari `frontend/web`:

```sh
VITE_DEV_API_ORIGIN=http://127.0.0.1:18090 npm run dev -- --port 5175
```

Jangan menjalankan server kedua jika port itu sudah aktif. Pada laptop teman,
default API 8080/frontend 5174 boleh dipakai jika image, env, CORS, migration dan
artifact cocok. Ikuti [backend README](../backend/README.md) dan
[migration guide](backend/POSTGRES_MIGRATION.md); jangan bagikan database password.

Pada verifikasi akhir, satu preflight sempat gagal di readiness cloud lalu
`/ready` dan preflight berikutnya kembali lolos. Penyebab sementara belum
dipastikan. Ulangi sebelum demo; jika readiness gagal, jangan menyembunyikan
hasil atau mematikan guard. Periksa koneksi database dan gunakan bukti tes lokal
sebagai alternatif, bukan mengklaim demo cloud sukses.

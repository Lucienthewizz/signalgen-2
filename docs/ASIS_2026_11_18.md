# Bahan asis SignalGen — 18 November 2026

Tindak lanjut arahan asis 11 November. Dokumen ini memisahkan yang sudah
diukur, yang sudah diuji dengan data sintetis, dan yang masih menunggu
keputusan atau masukan Prof.

## Ringkasan progres untuk asistensi hari ini

1. Screener memiliki mode seluruh katalog, watchlist, dan tanggal lampau.
   Hasil screening dapat diteruskan ke backtest dengan rule dan tanggal yang sama.
2. Evaluasi backtest mencakup harga tepat T+X, target dalam rentang, serta TP/SL.
   Hasil menampilkan win rate, return persen, hari target tersentuh, dan perbandingan
   evaluasi. Sinyal dihitung sebagai pengamatan independen; simulasi portofolio
   tetap merupakan mode terpisah.
3. Batas request yang menahan backtest seluruh katalog sudah diperbaiki.
   Screening kini menumpangtindihkan paling banyak empat request evaluasi dalam
   satu batch, dengan urutan penyimpanan tetap mengikuti katalog. Kecepatan
   gabungan terbaru belum diukur ulang untuk seluruh IDX di browser.
4. Arsip IDX mendukung publikasi parsial yang eksplisit. Bukti aktivasi lokal
   17 November mencatat 882 saham berhasil dan 80 gagal dari 962 anggota katalog,
   beserta scheduler yang berjalan dan dapat melanjutkan proses setelah restart.
   Ini catatan pengujian saat itu; kondisi layanan hari ini belum diperiksa ulang.
5. Sesi screening/backtest yang masih tertahan di server dapat ditemukan setelah
   reload. Pengguna membatalkan run sebelumnya secara eksplisit sebelum memulai
   lagi; hasil komputasi yang terputus belum dapat dilanjutkan dari titik terakhir.
6. Frontend terbaru merapikan dashboard, jurnal, berita, pengelolaan rule, dan
   informasi kualitas data per saham. Integrasi checkout Midtrans tetap berada
   di branch pekerjaan yang belum selesai; kesiapan pembayaran produksi belum
   dinyatakan atau diuji dalam pembaruan ini.

Pool worker backtest adaptif sudah diintegrasikan, tetapi pengujian terdahulu
belum membuktikan percepatan: median beban berat 3,36 detik untuk satu worker dan
3,46 detik untuk adaptif, memakai 23 saham sintetis. Jangan memakai angka ini
sebagai hasil seluruh katalog IDX. Lihat [uji ulang worker](frontend/ADAPTIVE_STUDY_SPEED_RECHECK.md).

Profil screening native Go atas arsip asli mencatat 1,06–1,36 detik untuk satu
hari pada jaringan lokal tanpa tambahan latensi, dan 109,4 detik dengan simulasi
80 ms per request. Hasil tersebut merupakan baseline sebelum optimasi pipeline,
belum memasukkan WASM dan IndexedDB browser. Lihat [profil screening](IDX_SCREEN_PROFILE_2026_11_17.md).

## Pengukuran backtest sebelumnya: 16 November

Pada asis lalu backtest seluruh katalog berjalan sangat lama. Pengukuran
16 November memakai data harian Yahoo asli untuk 882 dari 962 saham IDX
(80 ticker tidak punya data di Yahoo). Hasilnya:

- Perhitungan indikator, evaluasi rule, dan hasil T+X untuk 882 saham hanya
  butuh 0,3 detik (Oktober) dan 0,6 detik (satu tahun).
- Lambatnya berasal dari pembatas request server: 60 request per menit per
  user. Setiap saham butuh dua request (grant dan evaluasi rule), jadi
  seluruh katalog tertahan 14 menit walaupun perhitungannya cepat.

| Kondisi (882 saham, Oktober, T+3) | Waktu |
| --- | --- |
| Sebelum perbaikan, pembatas 60/menit | 14 menit 1 detik (14 menit menunggu pembatas) |
| Sesudah perbaikan, jaringan lokal | 0,62 detik |
| Sesudah perbaikan, simulasi jaringan 50 ms per request | 1 menit 21 detik |

Perubahan:

1. Request untuk backtest yang sudah diterima server tidak lagi dibatasi per
   menit. Setiap saham mendapat kuota tetap tiga kali percobaan, dan jumlah
   backtest bersamaan tetap dibatasi 32.
2. Browser mengambil data dan izin hitung untuk satu batch (10 saham)
   sekaligus, paling banyak empat request bersamaan.

Batas: angka di atas belum mencakup waktu WASM dan penyimpanan di browser
untuk seluruh katalog, dan latensi 50 ms adalah simulasi. Pengukuran memakai
data yang sudah tersedia. Pada mode default, cache yang masih kosong membuat
server mengambil Yahoo per saham (tiga sekaligus per batch); karena itu
scheduler dan arsip IDX perlu aktif agar backtest tidak menunggu Yahoo. Detail ada di
[pengukuran seluruh katalog](backend/WHOLE_CATALOG_STUDY_TIMING.md).

## Perlu keputusan atau masukan Prof

1. **Evaluasi rule tetap di server.** Indikator dihitung di browser, tetapi
   pencocokan rule tetap di server agar isi rule tidak terkirim ke browser.
   Setelah pembatas request diperbaiki, bagian ini bukan lagi penyebab lambat.
   Apakah perlindungan ini tetap diinginkan, atau rule boleh dievaluasi di
   browser?
2. **IndexedDB, bukan SQLite.** Hasil backtest disimpan di IndexedDB browser.
   Pagination dan ekspor 15.000 hasil sudah diukur (ekspor CSV sekitar
   0,1 detik). SQLite di browser perlu WASM tambahan tanpa manfaat terukur.
3. **Redis dan indeks database.** Data harga tidak diambil lewat query
   Postgres. Secara default server mengambilnya dari Yahoo dengan cache di
   memori; jika `SIGNALGEN_IDX_HISTORY_DIR` diisi, server membaca arsip IDX
   yang diisi scheduler. Karena itu Redis belum diperlukan untuk alur
   backtest. Indeks tambahan baru dibuat jika ada query yang terbukti lambat.
4. **1.000 user bersamaan.** Satu server menerima 32 backtest bersamaan dan
   menolak sisanya dengan pesan coba lagi. Target jumlah user dan topologi
   server (berapa instance) perlu disepakati.
5. **API real-time untuk paket mahal.** Perlu nama provider, dokumentasi API,
   biaya, dan izin penggunaan data.
6. **Screener real-time per paket.** Mode seluruh katalog memakai data harian.
   Screener real-time masih dibatasi 1–3 saham (Free) dan 1–10 saham
   (Analyst/Pro). Apakah screener real-time juga harus memindai seluruh pasar?
7. **Profit/loss dengan RR.** Return saat ini dalam persen. Perlu dipastikan
   apakah Prof ingin tampilan RR (misalnya 3:1) atau P/L nominal.

Prof juga menawarkan untuk menunjukkan aplikasinya; jadwal perlu diatur.

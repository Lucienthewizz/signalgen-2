# Backend observability — private, bounded operational logs

Implemented on `feature/backend-screening-reliability`. This is an operational
foundation, not a production load benchmark or a metrics dashboard.

## What it does

The Go entrypoint injects `platform/http.TrafficObserver` into the API. Every
completed request produces one JSON event on stdout, including Gin routes,
rejected CORS preflights and the raw WebSocket boundary. Fields are allowlisted:

- `request_id`: generated by the server, not accepted from a client header;
- `method`: a fixed HTTP-method allowlist, unknown methods become `OTHER`;
- `route`: a server-registered template, such as `/api/v1/rules/:id`;
- HTTP `status`, `duration_us`, `http_response_bytes`, `panicked`, and `aborted`.

Bodies, header values, query strings, bearer/session tokens, socket tickets,
emails, user/resource IDs, IPs, provider errors, and panic values are not logged
by this observer. Missing paths become `_unmatched`; intercepted preflights
become `_preflight`. The counter map has at most 128 normal route/method keys
plus one `_overflow` bucket even if server code misuses route labels.
Request IDs appear in log events, response headers, and existing JSON errors.
Allowed frontend origins can now read `X-Request-ID`, `Retry-After`, and `ETag`
through `Access-Control-Expose-Headers`; this does not expose credentials or
enable cross-origin access for other origins.

Counters include request/status-class counts, bytes, panics, duration sums/maxima
and in-flight handlers. A summary is emitted every minute, on shutdown cancellation,
and after ordinary HTTP handlers drain. Counters reset on process restart and
are not persisted in Supabase. Summary memory values are Go heap/runtime
allocation counters, **not process RSS or CPU**.

Gin recovery uses a local middleware instead of its default request/panic dump.
A panic before response commitment returns HTTP 500 with the existing error
envelope, `INTERNAL_ERROR`, request ID and `private, no-store`. After commitment,
the connection is aborted without appending JSON or claiming the already-sent
status changed. `aborted=true` flags incomplete responses; status 0 means an
intentional transport abort before any HTTP status was committed, not a fake
HTTP 200. Panic values are never dumped by this recovery middleware.

## WebSocket meaning and limitations

`GET /api/v1/screener/ws` keeps the raw transport through a ResponseController-
compatible writer. Upgrade/hijack and flush are preserved; no frame buffering
is introduced.

- Successful hijacking is recorded as HTTP 101, not HTTP 200.
- 101 means an upgrade happened, **not** that private scoring succeeded.
- Duration covers the socket handler lifetime, including client think-time,
  not just CPU calculation time.
- HTTP bytes exclude the handshake written through the hijacked socket and
  all WebSocket frames; they are not total network traffic.
- In-flight counts include socket handlers, not users or durable app sessions.

The feature protocol still owns `screener.result` / `screener.error`. Separate
screening observations now record outcomes and stage timings; see
[screening observations](SCREENING_OBSERVABILITY.md). Provider/cache counters,
histograms, distributed aggregation and separated client/server CPU/RAM
measurements remain follow-up work. These counters do not complete the thesis
evaluation.

## Reading order and local inspection

1. `backend/internal/platform/http/traffic.go`: observer, counters, safe fields.
2. `backend/internal/platform/http/traffic_writer.go`: transport compatibility.
3. `backend/internal/platform/http/router.go`: Gin adapter and safe recovery.
4. `backend/internal/api/routes.go`: request ID → observer → CORS → Gin/raw WS.
5. `backend/cmd/api/main.go`: injection and summary lifecycle.
6. `backend/internal/api/screener/observation.go`: request-local screening trace.
7. `backend/internal/platform/observability/screener.go`: bounded screening logs.

From the repository root, after starting the latest Go API:

```bash
docker compose logs --tail=50 go-api
curl -i http://127.0.0.1:8080/health
```

Illustrative event, not a measured result:

```json
{"msg":"http_request","request_id":"req_example","method":"GET","route":"/health","status":200,"duration_us":100,"http_response_bytes":16,"panicked":false}
```

There is no public `/metrics` endpoint. Container log access must remain private.
Compose bounds Go API logs to three 10 MB files with the Docker `json-file`
driver. Cloud retention and reverse-proxy logs do not inherit this protection:
production proxy logs must omit/sanitize the WebSocket `ticket` query parameter.
Collectors, access/retention policy and proxy/TLS need deployment review.
Compose log options apply when the Go container is recreated, not to an old
container that is already running.

## Regression checks

Tests cover concurrent snapshots, bounded labels, secret canaries, panic
redaction, recovery without an observer, partial-response aborts, CORS/unknown
paths, bytes, informational headers, flush/unwrap, a real WebSocket upgrade,
ticket/replay lifecycle and PostgreSQL/Model A contracts with the observer enabled.
They use isolated fixtures/databases, not real Supabase users or production secrets.
Screening checks additionally cover malformed/binary/oversized frames, permission
rechecks, shutdown cancellation, unsuccessful result writes, panic-stage retention,
concurrent snapshots and suppression of client IDs/payloads/raw errors.
